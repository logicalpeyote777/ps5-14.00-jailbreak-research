Abstract

This note records what was found, and how, during a two-day offensive characterisation of PlayStation 5 firmware 14.00 reached through the system User's Guide browser. Five userland primitives were confirmed on device (§1.1). CVE-2026-43720 is present on 14.00 and its re-entrancy is unguarded on this build — the trigger returns distinct inner/outer wrappers (same=false) — and the reclaimed object yields a bidirectional read/write proven in both directions as separate assertions, alongside an independent TransformStream iterator confusion, a bounded heap-pointer disclosure through FontFace reclamation, a WebProcess ROP frame reaching six controlled system-call arguments, and a hard map of the Web APIs the guide sandbox exposes. The kernel-side question — whether the oid_kind swap used as a black box since 13.60 does what its name suggests — was answered from a 103 MB symbol-less dump of firmware 13.60, the only image available (§6.0). It does not: the swap leaves CTLTYPE untouched and invisible to every type dispatch in the sysctl zone, and changes one test/je pair at 0xffffffff9e947f49 that makes the kernel skip the PRIV_SYSCTL_WRITE check. It is a permission bypass, not a type confusion, and not by itself a write primitive; under that reading the OID image yields 303 writable OIDs against 332 read-only. What remains unsolved is two independent gaps — a WebKit code leak is missing, and no kernel bug yielding read/write has been found — with seven candidate routes to the leak closed on device by seven different classes of evidence, including a bit-level round-trip that localises flush-to-zero to the float setter path rather than to JavaScript's number model, and the discovery that libkernel_web is xotext — execute-only text, so reading it through a read/write primitive faults — and the resulting reframe of the leak from reading code to reading data that contains code addresses. The engagement's largest defect was in its own tooling: a reporting helper rewritten without a return silently broke 125 of 146 probes while they kept reporting normally.

1. Introduction

Two findings anchor this note: a set of userland primitives in the PlayStation 5 User's Guide browser, confirmed live on a single console, and a correction to a piece of folklore.

The folklore is the sysctl kind swap. Since firmware 13.60 the community has carried a one-byte kernel write target described as "flip the sysctl kind field from 0x80048002 (read-only) to 0x70048002 (writable)" — a black box that asserts the swap makes a read-only sysctl writable, used that way in published variant analyses with no account of why the kernel would agree. This note opens it. From a live kernel dump with no symbol table, the swap was traced from the sysctl entry through the permission-check chain to the exact instruction whose flags it changes, and three things came out that the folklore does not capture:

  1. The type field is not involved. CTLTYPE is kind & 0xf; both values give 2 (CTLTYPE_INT), and all ten type-dispatch sites in the sysctl zone are blind to the swap. Whatever this is, it is not a type confusion.
  2. What changes is one branch. A single test eax, 0x10000000 / je pair at 0xffffffff9e947f49 decides whether the kernel runs a privilege check at all.
  3. The skipped check is a privilege check, not a MAC check. Its selector constant resolves to 241 and 242 — upstream FreeBSD's PRIV_SYSCTL_WRITE and PRIV_SYSCTL_WRITEJAIL. The skipped bit is CTLFLAG_ANYBODY.

The consequence is narrower than the folklore implies: the swap removes an early exit and does not open a new path — it makes an OID permitted to be written by an unprivileged caller, but does not make the kernel copy attacker bytes anywhere.

1.1 What is established on device

Before the kernel result, it is worth stating plainly what this engagement has, because the userland side is not folklore and does not depend on the kernel question at all. Three things were confirmed live on the 14.00 console, and each carries its raw output rather than a summary.

CVE-2026-43720 is present and its re-entrancy is unguarded on this build. The trigger probe fired the getContext() getter re-entrantly and got back two distinct wrapper objects:

TRIGGER   getter=1  inner=true  outer=true  same=false
note: "distinct inner/outer wrappers - reentrancy NOT guarded on this build"
outcome: VULNERABLE

[device] The same=false is the whole enabling condition. On a build where re-entrancy is guarded, the inner and outer calls return the same wrapper and there is no window. Here they do not, and the window exists.

The reclaimed object gives a bidirectional read/write, in both directions, proven separately. This is the load-bearing result of the userland side:

SPRAYED   n=80
WRITE     ok=true  a=99.001
CHANNEL   match=true  a=11.110011
ALIAS     idx=3
REVERSE   bidirectional=true
outcome: VULNERABLE
detail: {sprayed: 80, channel: true, write_ok: true, alias_idx: 3,
         bidirectional: true, prop_alias: true}

[device] Two directions were tested as separate assertions, not inferred from one. WRITE carries a value in through the public setter and CHANNEL confirms it landed with a different value (99.001 written, 11.110011 read back through the alias — the alias is a distinct object, not a mirror of the writer). REVERSE then proves the opposite direction independently. prop_alias: true records that the aliasing holds through property access, not only through the method surface.

A second, orthogonal confusion exists at the iterator level. ntfusion-iterator-confusion returns CONFUSED with a differential inside it: a control-conforming iterator does not throw where a plain object does.

variants: [ {label: "control-conforming", threw: false, verdict: "no-throw"},
            {label: "plain-object",       threw: true,  ctor: "TypeError"}, ... ]
outcome: CONFUSED

[device] This is reported as a reachability gate, not a primitive — see §3.4. It confirms a confusion exists but does not by itself yield a read or a write.

What the chain currently is, stated exactly. Re-entrant getContext() → distinct inner/outer wrapper → same-type reclaim of the freed slot → bidirectional read/write over the reclaimed object. Every link in that chain is confirmed on device. What the chain does not yet reach is an address: the primitive reads and writes a window it cannot locate, which is the code-leak gap of §6.1 and not a defect in the chain.

Where the novelty actually sits, and what backs it. The userland primitives are confirmations of a known CVE on a new firmware — valuable as a device measurement, not as a novel finding. The novel contribution is the kernel characterisation in §4: that the oid_kind swap is a permission-check bypass rather than a type confusion. That claim is backed by three independent static observations (the untouched CTLTYPE nibble across ten dispatch sites, the single moved test/je pair at a named address, and the privilege-selector constants resolving to 241/242) and by a novelty survey finding zero prior published characterisation of it (§8.4). The distinction matters for how much weight to put on each part of this note: one half is confirmed measurement of known things, the other half is a new reading of something everyone else used as a black box.

2.2 Getting arbitrary JavaScript into the guide

The User's Guide is an embedded WebKit WebProcess pinned to manuals.playstation.net; the entry is a DNS rewrite pointing that host at a LAN server serving an instrumented page instead of the manual, implemented in AdGuard Home on 192.168.1.70. The active config, read back rather than assumed:

Whether the shell path yields a less constrained WebProcess is [not tested].

2.3 The console as a self-driving instrument

The page polls GET /plan every 2.5 s, executes whatever module the server hands it, and phones home via POST /log. Two properties did the heavy lifting:

  • One module per plan. A module that crashes the browser kills only itself; the queue survives. Crash isolation is a scheduling property, not a coding convention.
  • A two-layer watchdog. A client-side Promise.race against a wall-clock deadline, plus a server-side MODULE_MAX_WALL. A hung module is skipped rather than stalling the queue.

Plans 1–5 of the definitive WebKit run executed with zero operator interaction after the initial page load. [device]

3.2 Canvas re-entrancy: the read/write primitive

A use-after-free reached by re-entering getContext() from inside the dictionary conversion of an outer getContext() call. Three modules, run in sequence [device]:

CVE-2026-43720-trigger     -> VULNERABLE      same: false    getter: 1

                                                reentrant: true

                                                write_ok: true
                                                bidirectional: true

getter: 1 is the load-bearing field in the first line: the settings getter is not guarded against re-entrancy. bidirectional: true is the load-bearing field in the third: the primitive reads as well as writes, which makes it a search tool and not only a modification tool. prop_alias: true with alias_idx: 3 confirms the attacker-controlled handle and the reclaimed object alias the same memory.

Upstream characterises the same bug (WebKit bug 313175) as unpatched on 14.10, confirmed by probe p553 on 2026-10-26, with the writable surface being the 6×float64 transform matrix plus seven numeric properties over a 768-byte Canvas2D context. 14.00 (2026-09-16) predates 14.10 (2026-10-01), so the finding transfers [upstream]. Memory was bounded deliberately: 1×1 canvases, a spray of 80, under the ~100 MB ceiling that killed an earlier plan.

3.3 Denormal-zeroing: why the primitive cannot read pointers back

The same run that confirmed the write also produced the engagement's most annoying negative:

CVE-2026-43720-leak  ->  integer-read-zero
                          channel: true
                          alias_idx: 6
                          nonzero_bytes: 0
                          raw_first32: all zeros
                          bigint_read: "0"

[device] The channel works, the alias is live, and every byte reads back as zero.

[device] The channel works, the alias is live, and every byte reads back as zero. The cause is the FPU mode the PS5's WebKit runs under: WebProcess heap pointers have the form 0x000000100xxxxxxx, whose exponent field makes the value denormal as an IEEE-754 double; with denormals-are-zero set the FPU reads 0.0. The pointer is present in memory and unreadable through any float64 lane. The workaround is a width change, not a location change: read through BigUint64Array or Uint8Array, which never enter the FPU.

The enabling condition on the write side is equally specific. ISO_MALLOC is off in the PS5 WebKit build (OptionsPlayStation.cmake), which is why engine-written pointers land in storage script can subsequently read; had isolation been on, the bidirectional result of §3.2 would not have been reachable at all.

Gadget offsets from the WebKit module's wk_gadgetmap: ret 0xC7, pop rdi 0x288B2, pop rsi 0x14EAD, pop rdx 0xFA7A2, pop rcx 0x80597, pop rax 0x3C98E, pop rsp 0xA1138 (pivot), pop r8 0x8CE7C, pop r9 0x80596, mov [rdi],rsi 0xC05B6, mov [rdi],rax 0x3881F, mov [rdi],eax 0x38820, mov rax,[rax] 0x6FD92, add rax,rcx 0x319FE4.

Test results: the 6-arg frame is 21 words with 6 controlled arguments, gadget order strictly increasing, every argument immediately following its gadget. The 4-arg degradation is 15 words / 4 args. A malformed 10-word frame returns -1 rather than a wrong answer.

This settles a live contradiction in the community corpus. One published gadget catalogue states "Not found: pop r8, pop r9 … (confirmed absent in full 4.6 MB scan, probes 272a/386a). Max 4 controlled syscall args." Another published table lists ["pop r8; ret"] = 0x991. Both are correct, about different binaries. The four-argument limit belongs to the game eboot used by the loader path. The WebProcess has pop r8 and pop r9. The kind swap can be driven from the browser through a real system call.

3.7 Execute-only text: the constraint that reframes the leak

The PS5 system libraries (libkernel_web) are xotext — execute-only text. Reading that code through a read/write primitive does not return garbage and does not return zeros; it faults.

"Signature-scanning libkernel text is impossible (the libraries are xotext; reading code through the R/W primitive faults and kills the process)."

[upstream] 1nk1/PS5-Prolapse, docs/PROJECT_HANDOFF.md §9.2 — from a working jailbreak, hardware-verified on 13.60. The scope of this claim is libkernel, and nothing more. Both occurrences of xotext in the handoff (lines 381 and 853) name libkernel; neither mentions WebKit. Whether WebKit's text is also execute-only is not asserted by the source and not tested by us — and §3.7.2 will argue that it does not need to be known.

The same source confirms the corollary that the static route is closed for them too: "there is no 13.60 [sprx] locally, which is precisely why the runtime calibrate tile exists." We verified the same on our own host: find /opt/AGENTS/Ares -iname "*.sprx" returns nothing, and ps5-sys.pup yields no readable .sprx string through its encrypted L1.

3.7.1 What the constraint does and does not close. The plan carried through most of this research — "scan WebKit text for 5f c3 / 5e c3 / 5a c3 / 59 c3 and rebuild the gadget map" — is closed, but the accurate statement of why matters. For libkernel the closure is hard: reading the text faults. For WebKit the stronger and better-supported statement is not that the scan cannot be run but that it is not the route taken by the people who have this working — they have never read a single byte of WebKit code. That claim does not depend on assuming WebKit is xotext, and it is the one worth carrying.

There is a cross-check already in the record: the community wk_gadgetmap contains no 0f 05. That is consistent with the text being unreadable, but it is not proof of it — the absence is equally consistent with the map having been built by a method that never read the text either, which is what §3.7.2 shows.

3.7.2 The reframe — read the address, not the code. This is the more useful product of the finding.

How the problem was posed for weeks How it has to be posed
leak the WebKit base by reading code leak the base by reading data that contains code addresses

The code is not needed; the address is, and addresses live in readable data. Their derivation (main.js:158-212) never touches a text page:

let textAreaVtPtr = p.read8(p.leakval(textArea).add32(0x18));
let textAreaVtable = p.read8(textAreaVtPtr);

On 9.00+ the active path is a JS global holding a code address, minus a candidate offset, with range and page-alignment validation — ctor - hc checked into the 0x8…0 / 0x4000-aligned window. The pre-9.00 legacy path reads the vtable, which lives in .data.rel.ro: data, not execute-only text. That legacy branch fired 0 times across 81 recorded runs. The whole method is "read the address of the code from the data", never "read the code".

We cannot copy their harness outright: their method reads the stack of a worker, and worker is SecurityError in the guide WebProcess (§3.1). The conclusion is more useful than a prohibition would have been. We do not know whether WebKit's text is readable, and we do not need to: the working method never touches it. That is a weaker-looking and considerably stronger claim than a generalised ban the source does not support.

4. The sysctl kind swap: what it actually does

This section is the core of the note. Everything in it is [static] unless marked otherwise.

4.1 Finding the dispatch without a symbol table

With no symbols, the question "which function handles kern.osrevision?" cannot be asked directly. It was answered arithmetically.

The dispatch site:

0xffffffff9e94875e   4c 8b 7b 38      mov  r15, qword ptr [rbx + 0x38]

The handler is loaded from +0x38 of the OID structure. For kern.osrevision that yields base 0xffffffffa095a6e0; for kern.osreldate, 0xffffffffa095b3a8 (file 0x256b3a8).

The OID field map at the new base:

Offset Field kern.osrevision
+0x18 oid_number 3
+0x1c oid_kind 0x80048002
+0x20 oid_arg1 0
+0x28 oid_arg2 0x30b52 = 199506
+0x30 oid_name → "osrevision"
+0x38 oid_handler 0xffffffff9e6609e8
+0x40 oid_fmt —
+0x4c refcount —
+0x50 oid_descr —

The swap byte is byte-identical under both base conventions:

0x256b3b0 + 0x17  ==  0x256b3a8 + 0x1f  ==  0x256b3c7

[static] This identity is why the community's published swap offset survives a change in how the structure base is counted.

4.2 The swap is one byte

0x80048002  ->  0x70048002
XOR           =  0xF0000000
little-endian :  02 80 04 80  ->  02 80 04 70
differing byte index: 3

[static] Verified by simulation on five OIDs — osrevision, osreldate, ncpu, pagesize, byteorder. One byte, at oid_kind + 3.

4.3 The type field is untouched

CTLTYPE is kind & 0xf. [upstream] sys/sys/sysctl.h: #define CTLTYPE 0xf, CTLTYPE_INT 2.

oid_kind & 0xf & 0x10000000 je at 9e947f4e
0x80048002 2 0x0 taken
0x70048002 2 0x10000000 not taken

The type is 2 before and after. A scan of every reader of [reg + 0x1c] in the sysctl zone found 17 sites; the masks applied immediately after the read were 0xf ×10 (none of them a swapped bit), 0x81000 ×1, 0x2000000 ×1, 0x1000000 ×1, and 0x10000000 ×1 — the only one that touches a swapped bit.

[static] The swap is invisible to type dispatch. It is not a type confusion.

4.4 The one branch that moves

0xffffffff9e947f45   41 8b 47 1c      mov   eax, dword ptr [r15 + 0x1c]
0xffffffff9e947f49   a9 00 00 00 10   test  eax, 0x10000000

241 and 242 are not arbitrary. [upstream] sys/sys/priv.h:

And the selector bit 0x04000000 is CTLFLAG_PRISON — "Prisoned roots can fiddle". The shape matches upstream sysctl_root() exactly:

/* Is this sysctl writable by only privileged users? */
if (req->newptr && !(oid->oid_kind & CTLFLAG_ANYBODY)) {
        int priv;
        if (oid->oid_kind & CTLFLAG_PRISON)
                priv = PRIV_SYSCTL_WRITEJAIL;
        ...
        else
                priv = PRIV_SYSCTL_WRITE;
        error = priv_check(req->td, priv);
        if (error)
                goto out;
}

[upstream] The bit the swap sets, 0x10000000, is CTLFLAG_ANYBODY — "All users can set this var". The swap sets it. The guard !(oid_kind & CTLFLAG_ANYBODY) becomes false. priv_check is not called.

This is the answer to the question the folklore never asked. The swap does not confuse the kernel about what kind of value this is. It sets the flag that says anybody may write this, and the kernel's own permission logic agrees.

4.7 Verdict

The kind swap is a permission bypass.

It is not a type confusion: CTLTYPE is unchanged and every type dispatch is blind to it. It is not a write primitive: it changes which branch the kernel takes, not what gets copied. The swap removes an early exit; it does not open a new path.

One address carries the entire console-verification burden: 0xffffffff9e947f49.

5.2 The CFI window

Handler dispatch is guarded by an identity test of the form sub rax, r15; ror rax, 3; cmp rax, N; ja reject.

For the sysctl dispatch site: A = 0xffffffff9e6616f8, N = 0x1a3 (419), admitting the range [0xffffffff9e6609e0 .. 0xffffffff9e6616f8] — 420 8-byte slots, 420/420 non-null. Admission is ror3(A − H) ≤ N with ror3(v) = ((v >> 3) | (v << 61)) & MASK.

The census that makes this an identification rather than a guess: 5,146 complete lea/sub/ror3/cmp/ja windows exist in TEXT. Of those 5,146, exactly one admits kern.osreldate's handler (ror3 = 0x81) and exactly one admits the shared ncpu/osrevision/pagesize/byteorder handler (ror3 = 0x1a2) — the same window.

[static] The sysctl handler window was identified by arithmetic, not by name.

5.4 The amplifier, and why it is not one

A natural follow-on: if a one-byte write can change kind, can it amplify into a bulk copy? Two one-byte primitives on the same field were designed — QUAD → STRING changes byte index 0 at struct + 0x14 to 0x03; QUAD → 0x70… changes byte index 3 at struct + 0x17 to 0x70. The storage target for ncpu, 0xffffffffa20fe8bc (file 0x3d0e8bc, u32 = 16), sits in a favourable neighbourhood:

arg - 8  = 0x0000000fffffffff
arg + 0  = 0x0000000000000010
arg + 8  = 0
arg + 16 = 0
arg + 24 = 0
arg + 32 = 0
arg + 40 = 0x0000ffff00000000
arg + 48 = 0x9f6caf8e00000000

32 zero bytes immediately follow — a low-collateral, self-verifying, reversible landing zone. The proposed amplifier: a 1-byte write at ncpu_struct + 0x14 = 0x03 so that sysctl({1,3}, 2, old, oldlenp, new, buf, N) copies N bytes into the 8-byte slot. It was falsified against the real __sysctl:

real __sysctl = sy_call slot 199 -> stub -> 0xffffffff9e9481e0 (file 0xab81e0), 418+ instr

[+0x14] reads:
  __sysctl                       0
  access check 9e92a130 (252i)  0
  OID lookup    9e649280 (192i) 0
  sysctl_req    9e648ff0 (202i) 0

Flag-constant search across all four: 1 hit
  movabs rcx, 0x800000000000   (a 48-bit mask, not a CTLFLAG)

[static] __sysctl builds a 0x60-byte sysctl_req on the stack ([rbp-0x110] = old, [rbp-0x108] = oldlenp, [rbp-0x100] = new). Dispatch is by function pointer (oid_handler), not by type field — changing copy semantics requires changing oid_handler, a CFI-guarded function pointer, not a byte. The amplifier as stated is falsified; the caveat carried honestly at design time — "whether the STRING handler copies newlen without a length check is inference, not observation on this kernel" — turned out not to need resolving, because the dispatch model rules the whole approach out first.

It is a measured boundary: with a working bidirectional primitive on the reclaimed object, the reachable window contains no pointer, no code-shaped slot, and no size field that would amplify a read — and the float64 lane that could carry a pointer in cannot survive the setter to deliver one. The code leak is not hiding in the object we can already touch. Finding it requires a different object or a different primitive, and that is a stronger statement than its absence — it narrows where the next attempt should go.

Described in §2.3. The methodological point is the scheduling, not the code: one module per plan makes crash isolation a property of the system rather than of the module, and the two-layer watchdog means neither a crash nor a hang stops the queue. The engagement ran unattended after one page load.

7.3 Static analysis without symbols

No symbol table, so every identification is arithmetic:

  • CFI windows as fingerprints. 5,146 complete lea/sub/ror3/cmp/ja windows in TEXT; exactly one admits both known sysctl handlers — identified by arithmetic, not by name.
  • Slot-value identity over naming. fo_poll @ +0x20 proven by three file-operation tables (0xffffffff9feb7ca0, 0xffffffffa05e62b0, 0xffffffffa092f528) each having only slot +0x20 inside the validated window [0xffffffff9e65b760 .. 0xffffffff9e65b7d8].
  • CFG entry counts as proof of unreachability. The §4.5 check block has exactly one incoming edge: "I did not see it reached" becomes "it cannot be reached".
  • BFS from the syscall entry. __sysctl 9e9481e0 → 9e947d90 → 9e9486f0 → call r15, with __sysctl holding zero indirect calls across 280 instructions.

7.5 Retractions

Five claims were retracted during the engagement. They are listed because each retraction taught something the surviving findings did not.

  1. The OID-list walk. Walking the sibling link at +0x08 from a known OID visited 5 nodes and named 1; from +0x00, 3 visited / 1 named; via +0x08 as list head, 3 visited / 0 named. Pointers landed on non-OID data — one hop yielded 0x20786c25006b636f, ASCII fragments. The layout is right; the traversal is not. An analogy that was not executed is not evidence.
  2. The amplifier. Falsified in §5.4: dispatch is by function pointer, not by type field.
  3. The kind-swap abandonment. An earlier note concluded that nothing on the sysctl(2) path reads oid_kind — 1,773 [reg+0x14] reads in TEXT across 955 functions, 0 of 16 readers inside __sysctl and its 15 direct callees. Correct and irrelevant: +0x14 is the wrong offset (the high half of the +0x10 pointer). The corrected +0x1c scan found the load-bearing reader at 0xffffffff9e947f45. A null result was read as a limit of the question, not of the tool.
  4. The nopoll leaf. Described as a "14-instruction leaf"; it is an 8-byte tail-jump (55 48 89 e5 89 f7 5d e9 84 d9 db ff). The earlier rets=1 counted the next function, because a ret-terminated bound walks straight through a tail-jump.
  5. The stub-slot misread. Every stub slot is 8 bytes: e9 <rel32> cc cc cc. Two stubs sit adjacent for alignment and the wrong one (+0x08) was read instead of +0x00; referencer arithmetic proves +0x00 (stub 0xffffffff9e656510 ← 0x1ac7cd8 → table 0x1ac7ca0 → +0x38 = fo_close). The retracted "walk = detach" belonged to code reached through the wrong stub.

Three method bugs were found en route and are easy to repeat: o.imm arrives signed from capstone (this silently broke a TEXT bound and produced call_targets = 0; mask with 0xFFFFFFFFFFFFFFFF); textual matching on "-0xc8" matched unrelated strings; and applying the static-file formula outside its domain — live runtime pointers carry the modern FreeBSD 13+ KVA prefix 0xffff8e77…, to which VA - 0xffffffff9e3f0000 returns nonsense.

7.6 CVE existence by direct query

Two CVEs in this note were verified against NVD directly (services.nvd.nist.gov/rest/json/cves/2.0) after a search engine returned nothing for one of them. The search engine was wrong.

For CVE existence, query NVD or MITRE directly. A search engine's null result is not evidence of non-existence.

The same discipline produced the syscall-number correction. The community's "sysctl = 202" traces to a syscall_map with 331 entries in which 199 is absent and 202 is present — someone matched the map's key 202 against FreeBSD's upstream number without reading the PS5 name table. The PS5 name table says otherwise, and the sysent table agrees:

Two numbering spaces, not one right answer and one wrong. The framing worth carrying forward is sharper than "the community got it wrong". Relapse's syscall_map and the PS5 native sysent table are two different numbering spaces, and the collision is that both contain a key that means sysctl in one of them:

Community syscall_map 0x0CA = 202 0xC7 = 199 is absent

The hazard is concrete: taking 202 from the community map and handing it to the native table does not fail — it calls a different syscall and returns something. A wrong number here is not an error; it is a wrong answer. SYSCTL_NR = 199 is correct for the native table, and was cross-checked three ways: the PoC's own constant, sysent-13.60.md, and an independent scan resolving idx 199 → 0xffffffff9e655a60.

7.7 Fuzzing the live kernel from the browser (proposed, not executed)

Upstream's variant analysis closes with a wish: a "baseline for diffing once someone gains any 14.x read access" — a chicken-and-egg, since the read access is what the baseline is for. The chain built here breaks the loop from the other side:

code leak -> syscall dal WebProcess -> fuzz syscall 14.00 -> bug kernel

With the ROP frame of §3.6 already reaching six controlled arguments and sysctl proven reachable at 199 (§7.6), the live 14.00 kernel becomes fuzzable from the browser, without the image and without a prior kernel primitive. The syscall surface is the fuzz target; the crash oracle is the page dying and the synchronous beacon (§7.8) recording exactly where.

Two caveats, so this is not mistaken for a result: nothing here was executed — the chain's first link is the same missing code leak of §6.1 — and it is a route to a bug, not a bug: the guide WebProcess may be too constrained for the interesting call classes, and the crash oracle available from the browser is the same weak oracle discussed in §7.4. It is recorded because a dead end mapped is more useful to the next reader than one omitted.

7.8 The patcher that did not patch: a silent false negative at scale

The most consequential defect found in this engagement was not in the target. It was in our own automation, and it was invisible for most of the engagement's lifetime.

The mechanism. Every probe module carries its own reporting helper:

function post(ev, d) { /* ... */ }

The helper was rewritten from asynchronous fetch to synchronous XHR — a change that was correct in principle, and taken from upstream's own comment that a synchronous beacon "leaves the renderer before a possible crash in the same call". But the rewritten helper had no return statement, so it returned undefined.

125 of 146 modules call post(...).then(...). With fetch those calls were chaining onto a real Promise and worked. With synchronous XHR they chained onto undefined:

TypeError: undefined is not an object (evaluating 'post("pg_begin", { module: MODNAME, tier: "offsetmap" }).then')

[device] The signature appears verbatim in the probe log against alias-pointer-scan-1400. The count was confirmed by static analysis of the module corpus at each generation:

Corpus generation Modules calling post().then with XHR with fetch
pg_tests.json.pre-syncxhr.bak 145 124 4 144
pg_tests.json.pre-postfix.bak 146 125 146 24
pg_tests.json (fixed) 146 146 146 24

[static] Counted over the retained backups, which is why the regression is visible at all.

The fix was to return a no-op thenable, so the existing .then(...) call sites keep working against a synchronous transport:

return { then: function (f) { try { if (typeof f === 'function') f(); } catch (e2) {} return this; },
         catch: function (g) { try { if (typeof g === 'function') g(null); } catch (e3) {} return this; } };

146/146 modules patched, zero syntax errors. The recovery was not cosmetic: 53 modules came back from skipped, among them CVE-2026-43715 (FontFaceSet UAF) and CVE-2026-43720 (Canvas UAF) — modules that had never actually run on the device despite having been swept.

The second-order lesson: the patcher that patched nothing. The first attempt at the corpus rewrite used a regex that held two levels of nesting. The helper has three (function { fetch( { body: JSON.stringify( {…} ) } ) }). The regex matched zero modules — and reported success.

A patcher that does not patch and does not say so is worse than a broken patcher. A broken patcher fails loudly. This one left 145 probes silently in the pre-fix state while reporting the job done, and the failure only surfaced because the next change made it observable.

This is the exploit-development analogue of a test suite that passes because it never ran. It is worth stating as a general hazard rather than an anecdote: automation that transforms a corpus reports what it intended, and unless the output is independently counted against the input, "0 files changed" and "145 files changed" both arrive as exit code 0.

Why the synchronous XHR was worth the trouble anyway. With asynchronous fetch, a run that crashed the page left nothing behind — the beacon was still queued when the renderer died. With the synchronous transport, every run delivers the exact point of death. That is directly why the FontFace branch in §6.2 could be localised to document.fonts.load() at all: without the synchronous beacon, those fifteen runs would have been fifteen silences, and the branch would still be open and unexplained.

A second instance, downstream this time: the tolerant constructor. The same silent-false- negative signature reappeared later in the day at the other end of the pipeline. A byte-channel probe read a length off an object that did not have one:

id.length                        -> undefined
new Uint8Array(id.length).length -> 0        <- an EMPTY array, not an error
scan                             -> 0 hits  <- structural false negative

new Uint8Array(undefined) does not throw and does not warn: it produces an empty array. A wrong type handed to a tolerant constructor yields a emptiness that looks like a result. The patcher produced its false negative upstream — it patched nothing and said it did; this one was produced downstream, inside a constructor that accepts anything. Two different points in the pipeline, the same silent signature.

The countermeasure is the same lesson applied twice: report the type alongside the value. In the pixel case it was a control that printed length and type separately —

CTRL-BASE   len=undefined  type=ImageData

[device] pixel-bytewrite-1400, UA PlayStation 5/14.00 — and that separate type field is what made the undefined visible. Had only the count been reported, the byte channel would have been written off on an artifact.

A third instance, and the most instructive: a crash read as a broken primitive. For most of the engagement a page dying on a read looked like the primitive failing under some alignment or permission edge. Under xotext (§3.7) the reading inverts: the primitive was working correctly against a protection we did not know was present. The crash was information, not noise — it was telling us the address was code and code is not readable. We had the signal the whole time and had filed it under failures. [hypothesis] — the inversion is a re-reading of our own crash log through a mechanism established upstream on libkernel; we have not attributed individual crashes to it.

The general form is worth stating: a crash is a result, and it has to be classified rather than discarded. A death attributed to "the primitive is flaky" closes a line of inquiry; the same death attributed to "the page is execute-only" opens one. The difference is not in the event, only in what is done with it.

The canary trap: the most-repeated candidate is the least trustworthy. From the same upstream handoff, a detail that cost real runs and generalises badly. When scanning a stack for values that look like return addresses:

25 of 38 candidates were libkernel+0x751D0 = __stack_chk_guard — a data word copied into many frames, not a return address.

[upstream] Independently confirmed there against OFFSET_lk___stack_chk_guard. The trap is the inverse of a strong intuition: a pattern that recurs across many frames feels like the loudest signal available, and here it is the weakest — it recurs precisely because it is a constant being copied, not because it is the thing being sought. Frequency is evidence of persistence, not of identity. A candidate set that clusters hard on one value should be treated as having found a constant until proven otherwise.

The three instances share one shape: the negative was not in the world, it was in the reading of it. A helper that returns undefined, a constructor that swallows it, a protection that faults on a legitimate read. In each case the fix was not a better probe but a better classification of what the probe already returned.

The two facts are the same fact from either side: the transport determined whether a negative result was readable. A crash with no beacon is indistinguishable from a crash that never happened, and an empty array is indistinguishable from a scan that found nothing.

8. Related work and novelty survey

The survey was run against primary sources — GitHub's API and raw file endpoints — rather than a search engine, for the reason given in §7.6.

8.1 The community 14.10 corpus

ZigZagBoi1/PS5-14.10-Research is the largest body of work in this area: an active community effort with 2,901 probes, 3,245 captures and 155 merged PRs at clone time (315 MB, 9,005 paths, 428 documents). It documents the same CVE-2026-43720 canvas reentrancy, the same DAZ blocker, the same FontFace reclaim leak with the same +0x58/+0x68 offsets, and the same conclusion that the info leak is "the sole remaining blocker for the entire 14.10 exploit chain". Our userland findings are consistent with it and, in the ntfusion iterator confusion, add a primitive the corpus does not carry on 14.00.

On the kind swap, the corpus documents the technique and not the mechanism. The published variant analysis describes a flipOidKind step — flipping the OID kind field from 0x80048002 to 0x70048002 via a decrement primitive — with the offsets and intended effect, but not the branch that changes, the privilege skipped, or the fact that CTLTYPE is untouched. A targeted search is the cleanest statement of the gap: grepping all .md, .c, .js and .lua files for ANYBODY, priv_check, PRIV_SYSCTL and securelevel_gt returns no hit anywhere in connection with the sysctl kind swap — the hits that exist concern other handlers entirely (sys 598, sys 612/649, RDMSR, PRIV_NETINET_SETHDROPTS). The corpus's own sysctl write attempts on 14.10 all returned -1, and its own audit re-classifies them honestly as "one failed write attempt, not a survey proving all sysctl writes blocked".

8.2 Relapse

Relapse is the published exploit whose WebKit stage this engagement attempted to port. Its syscall_map is the origin of the "sysctl = 202" error (§7.6); its kernel stage stops at 13.60; its WebKit stage is dead on 14.00 for the reason established in §3.5. Its wk_gadgetmap did settle the pop r8 / pop r9 question for the browser path (§3.6).

8.3 Upstream FreeBSD

Upstream sys/kern/kern_sysctl.c, sys/sys/sysctl.h and sys/sys/priv.h were the naming reference for §4.4: the PS5 gate order matches upstream sysctl_root() (writable, securelevel, ANYBODY/privilege, handler, MAC), and the selector constants match (0x04000000 = CTLFLAG_PRISON, derived esi 241/242 = PRIV_SYSCTL_WRITE/PRIV_SYSCTL_WRITEJAIL). But the bit values verified structurally on the PS5 dump are 0x40000000, 0x08000000, 0x10000000, 0x04000000, 0x80000000 — the names attached to them are a FreeBSD convention assumption. The PS5 kernel is a Sony-modified fork; the numbering was not independently enumerated on the PS5 side.

8.4 Novelty verdict

No prior art found that documents the kind-swap mechanism at branch level.

What is prior art: the swap as a technique — byte values, target offset, intended read-only→writable effect — published community knowledge carried since 13.60 and described in the 14.10 corpus's variant analysis; the canvas reentrancy UAF, the FontFace reclaim leak, the DAZ blocker and the info-leak-is-the-blocker conclusion; and the wk_gadgetmap gadget set.

What is not prior art, and is contributed here:

  1. The specific branch the swap moves — test eax, 0x10000000 / je at 0xffffffff9e947f49 — and what it guards: the PRIV_SYSCTL_WRITE/PRIV_SYSCTL_WRITEJAIL check, with the swap setting CTLFLAG_ANYBODY rather than confusing a type.
  2. The CFG proof that the check block has exactly one entry and the swap closes it, with the three-way separation of "check denies when executed" / "our OID never executes it" / "the swap is load-bearing".
  3. The CFI-window census (5,146 windows, exactly one admitting both handlers) locating the dispatch site without symbols, and the 303-writable / 332-read-only OID enumeration under the corrected offset.
  4. The falsification of the type-field amplifier, and that the earlier abandonment rested on the wrong offset (+0x14 not +0x1c).
  5. The ntfusion iterator confusion on 14.00 as a second orthogonal WebKit confusion, scoped to reachability of the confusion path — not an obtained read/write object.
  6. The six closed code-leak branches of §6.2, each closed by a different evidence class so the set has no shared failure mode — including running upstream's p563 verbatim to remove interpretation as a variable, and a write-channel round-trip that measures where FTZ lives instead of inferring it from a null scan.
  7. The silent-false-negative case study of §7.8 — a methodological result about automated exploit development, not about the PS5.
  8. The xotext constraint on libkernel_web established, and the resulting reframe of the code leak from reading code to reading data that contains code addresses (§3.7) — including the field-by-field delta stability table showing the deltas are a property of a build family, not of the module, and that thread_list moves even within 12.xx.

The honest summary: the swap was known; why it works was not. This note supplies the second half, and in doing so narrows what the first half is worth — a permission bypass is a smaller thing than the folklore's "makes it writable" implies, and a smaller thing stated precisely is more useful than a larger thing assumed.

9. Conclusion

Two things were established and one was corrected.

The userland result is a set of confirmed primitives on PS5 14.00 in the guide browser: a bidirectional canvas UAF, an independent TransformStream iterator confusion, a bounded heap-pointer disclosure, and a ROP frame reaching six controlled system-call arguments — all bounded by a sandbox that refuses workers with SecurityError and has no SharedArrayBuffer.

What is missing has not changed, and it is two gaps, not one: a WebKit code leak is missing, and a kernel bug yielding read/write has not been found — and per §6.1 finding the leak will not supply one. One caveat travels with every kernel number here: the image analysed is 13.60 and no 14.00 image exists (§6.0), so the device results stand on their own while the kernel characterisation remains a hypothesis. With a code leak in hand the 14.00 kernel can be fuzzed live from the browser (§7.7), routing around the missing image entirely — a proposal, not a result.

The most useful product may be neither finding but the discipline behind them: run the gate against a known negative before trusting it on an unknown; treat a probe that never touched its subject as having said nothing; and when a null result shows up, check the offset before concluding the tool has a limit. The six closed branches of §6.2 are worth what they are only because each was closed by a different kind of evidence — and the largest defect found here was in the engagement's own automation, where a helper missing one return quietly broke 125 of 146 probes while they kept reporting normally (§7.8). Automated exploit development reports what it intended; unless output is counted against input, a patch that changed nothing and a patch that changed everything both exit zero.
